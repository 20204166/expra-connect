This patch productizes the headless connection core with `ConnectRuntime`,
configurable discovery, durable profile state, lifecycle fencing, live grant
updates, dynamic versioning, release tooling, installers, and integration docs.
The current debugging pass adds regression coverage and fixes confirmed defects
found by focused runtime probes.

**Finding A2: discovery callback can resurrect peers after shutdown**

- Evidence: `runtime.py:354-360` checks generation and `started` before the
  callback performs its validation and writes `_peers`; `shutdown()` increments
  generation and clears `_peers` at `runtime.py:204-217`, but there is no shared
  lock around the check/write sequence.
- Exact counter-test command:
  `python - <<'PY' ...` started a runtime with discovery disabled, blocked
  `_trusted_candidate_is_valid` in a separate callback thread, called
  `shutdown()` while the callback was blocked, then released it and inspected
  `runtime.peers`.
- Evidence: reproduced `5 / 5` times. Final state was `stopped`, while
  `peers_after_shutdown=1`. This is deterministic with the synchronization
  barrier and does not require a live network.
- Verdict: **confirmed lifecycle bug, P1**. A stopped runtime retains a stale
  discovered peer and can invoke `on_discovery` after shutdown. The generation
  check is insufficient because it is not held through the mutation. This can
  leak post-shutdown events to callers and makes restart/stop state non-final.
- Uncertainty: the current default zeroconf callback may usually be stopped
  before this race is observed, but the callback is explicitly asynchronous;
  the direct deterministic probe proves the runtime boundary itself is unsafe.

**Finding A3: discovery backend-construction failure escapes startup**

- Exact counter-test command:

- Evidence: output was `exception= RuntimeError`, `status= starting`, and

  the listener has already started, with status left at `STARTING` and partial
  resources requiring cleanup.
- Verdict: **confirmed lifecycle/startup bug, P1**. A discovery plugin/backend
  failure violates the runtime's documented graceful discovery degradation and
  leaves an externally observable partial-start state.
- Uncertainty: a factory that raises is an injected extension failure rather
  than the standard zeroconf backend's normal unavailable path. It is still a
  supported configuration seam (`discovery_backend_factory`) and must not leave
  the composition root half-started.

### Opposing Agent 2 - Repo-Truth Skeptic

#### Findings

1. **P1 - Runtime pairing approval bypasses the mature read-only pairing boundary and is not atomic**

   `ConnectRuntime.approve_pairing()` accepts arbitrary permission strings and
   calls `PairingManager.approve()` before `_wire_grants()` validates them
   (`src/expra_connect/runtime.py:157-163`, `:468-480`). The mature wire
   contract explicitly restricts pairing to `READ_PERMISSIONS` and reserves
   broader permissions for elevation (`src/expra_connect/wire_protocol.py:148-165`,
   `:182-200`). A direct runtime probe approved `process_termination` and
   installed it in the live service grant. A second probe using
   `not-a-permission` raised `ValueError` only after the grant had already been
   inserted into `pairing.grants`.

   This violates the documented separation that pairing is not authorization
   elevation and leaves failed approvals with mutated in-memory state that can
   subsequently be persisted by `shutdown()`. The current default runtime has
   no capabilities enabled, so the destructive operation is not immediately
   callable through that default path; the persisted/live ACL and public API
   contract are nevertheless wrong and become security-relevant when
   capabilities are supplied.

2. **P1 - Discovery backend construction can leak the listener and leave the lifecycle in `STARTING`**

   `RemoteSocketServer.start()` completes before `NetworkDiscovery(...)` is
   constructed, but `_server` is assigned only immediately before that
   construction (`src/expra_connect/runtime.py:285-300`, `:315-323`). The
   discovery backend factory is invoked by `NetworkDiscovery.__init__`
   (`src/expra_connect/discovery_full.py:264-270`), outside its failure-safe
   `start()` try block (`:317-329`). The runtime startup handler catches
   `KeyError`, `OSError`, `TypeError`, and `ValueError`, but not `RuntimeError`
   (`src/expra_connect/runtime.py:189-198`).

   A focused probe with a factory that raises `RuntimeError` showed the
   exception escaping, `status` never reaching a terminal state, and the
   listener port remaining open. This conflicts with the mature discovery
   contract that discovery failure leaves the application usable as a
   single-node app (`discovery_full.py:303-309`) and with the integration
   lifecycle promise that startup failure does not strand owned resources.

#### Repo-truth checks and disproven concerns

- The custom service-type fix matches the mature implementation: both the
  Zeroconf backend and normalization use the configured service type, and the
  focused custom-type test passed.
- The registry `cluster_enabled=False` default used by `ConnectRuntime` matches
  the integration contract that cluster participation is opt-in; the local
  record remains `AUTHORIZED` while membership is `NOT_JOINED`.
- The revocation fix preserves the registry's mature separation: it marks an
  existing record revoked without deleting membership or connection state, and
  the live `RemoteService` grant map is refreshed.
- Identity and transport fingerprints are distinct in the advertisement and
  trusted-candidate check. The focused wrong-transport-fingerprint test passed.
- Malformed trust state, invalid persisted permissions, concurrent start, old
  generation callbacks, and listener endpoint advertisement all passed their
  focused regressions. The malformed-state probes did not print credential or
  fencing material.

### Opposing Agent 3 - Architecture/Security Skeptic

Independent architecture/security review completed against the current worktree. No
application code or tests were changed. Counter-tests did not print secrets,
private keys, grant material, or fencing-token values.

#### Finding A3-1: `ConnectRuntime` does not compose network pairing handlers

- **Severity:** P1
- **Confidence:** High
- **Evidence:** `runtime.py:285-290` constructs `RemoteSocketServer` with only the
  service, host, port, and TLS context. It supplies none of the server's
  `pairing_handler`, `pair_confirm_handler`, `pair_abort_handler`, or
  `elevation_handler` seams (`server.py:86-90`). Consequently the listener's
  `pair_request` branch returns `pairing_unavailable` whenever the handler is
  `None` (`server.py:254-255`). `ConnectRuntime.approve_pairing()` is only a
  local in-process operation and is not connected to the network request path.
- **Counter-test:** Started a normal `ConnectRuntime`, connected through the
  real TLS listener using its advertised certificate fingerprint, and submitted
  a structurally valid read-only pairing request. The result was
  `network_pairing_result=False`; no pairing approval was reached.
- **Impact:** The advertised runtime cannot be paired by another node through
  the shipped listener. This is a composition failure at the trust bootstrap
  boundary, not merely an untested optional callback. It makes the network
  runtime unusable for the primary pairing flow while still exposing a listener.
- **False-positive concern:** A host could theoretically compose `RemoteSocketServer`
  itself and provide handlers, but `ConnectRuntime` is the public composition
  root and exposes no handler configuration. If this package intentionally
  delegates all network pairing to an external host, the runtime documentation
  and the public `begin_pairing`/`approve_pairing` API would need to state that
  boundary explicitly; current tests and patch summary describe a productized
  runtime instead.

#### Finding A3-2: Runtime starts with no advertised capabilities, so authenticated reads are denied

- **Severity:** P1
- **Confidence:** High
- **Evidence:** `_start_components()` hardcodes `capabilities=frozenset()` at
  `runtime.py:272-282`. `RemoteService._solve()` requires the operation's
  capability before checking the grant permission (`remote_service.py:381-389`),
  and `hello` plus all read operations require `NodeCapability.READ_STATE`
  (`wire_protocol.py:37-45`). `ConnectConfig` has no capability configuration
  that can replace this empty set.
- **Counter-test:** Started the runtime with discovery disabled, created a valid
  in-process pairing grant, and sent an authenticated `hello` through the
  constructed `RemoteService` using the transaction secret without printing it.
  The provider raised `RemoteAuthorizationError`, rather than succeeding.
- **Impact:** Even if the missing network pairing composition were repaired or
  a grant were provisioned locally, the runtime cannot serve the authenticated
  read contract. A peer cannot complete the normal hello/read lifecycle; the
  runtime's listener is effectively a TLS endpoint with an always-deny ACL for
  every defined operation.
- **False-positive concern:** Empty capabilities may be intentional for a
  deliberately inert shell, but that conflicts with the configured `provider`
  seam, the runtime's advertised `connectable` listener, and the productization
  summary. If capabilities are meant to be host-owned, the configuration must
  expose and validate them; silently hardcoding empty capabilities is not a
  usable default for this public runtime.

#### Finding A3-3: Trust persistence failures are reported only in logs and approval still succeeds

- **Severity:** P2
- **Confidence:** High
- **Evidence:** `approve_pairing()` mutates the pairing owner and refreshes the
  live service before calling `_save_persisted_state()` (`runtime.py:157-163`).
  `_save_persisted_state()` catches `OSError`, `TypeError`, and `ValueError`,
  logs a warning, and returns without changing runtime status or its result
  (`runtime.py:442-459`). The public method therefore returns the new grant even
  when its durable trust write fails.
- **Counter-test:** With a started runtime, patched the package state store's
  `save()` to raise `OSError("disk full")` during `approve_pairing()`. The
  approval returned a grant, the grant remained in memory, and status remained
  `started`.
- **Impact:** Callers receive success and the live listener authorizes the new
  grant, but a restart loses the trust state. This creates a false durable-trust
  signal and can leave the operator believing a peer is paired when the next
  process loses the relationship. It also makes failure recovery ambiguous: the
  caller has no transaction result indicating that persistence failed.
- **False-positive concern:** Best-effort persistence may be an explicit product
  policy, and the warning is useful diagnostics. However the patch summary calls
  the profile state durable, and startup already has a dedicated
  `PERSISTENCE_FAILED` state (`runtime.py:41-46, 193-198`). That makes silently
  succeeding after a failed trust commit inconsistent with the runtime's own
  lifecycle contract. No finding is made about atomicity of successful writes;
  the issue is the failure result and state transition.

### Opposing Agent 4 - External-Research Skeptic

#### Finding A4-1: Runtime advertisement version is not tied to the packaged version

- **Severity:** P2
- **Confidence:** High
- **Status:** Confirmed by repo inspection and an isolated wheel build
- **Evidence:** `pyproject.toml:7-10,21-22` makes the distribution version dynamic from
  `expra_connect._version.__version__`, and `src/expra_connect/cli.py:8,20` uses that
  same value for `--version`. However, `src/expra_connect/runtime.py:64-70` hardcodes
  `ConnectConfig.app_version` to `"0.1.0"`. `_start_components()` passes this value to
  both `RemoteService(..., app_version=...)` at lines 272-282 and
  `DiscoveryAdvertisement(..., app_version=...)` at lines 302-312.
- **Impact:** If a release changes `_version.__version__` without every host explicitly
  supplying `app_version`, the wheel/CLI report the new release while discovery TXT
  metadata and the remote status report `0.1.0`. Consumers using advertised app
  version for diagnostics, compatibility display, or rollout checks receive stale
  information. This does not alter the wire protocol version, which remains separately
  represented as `"1"`.
- **Reproduction/evidence test:** The wheel built from the current tree was
  `expra_connect-0.1.0-py3-none-any.whl`, with metadata `Version: 0.1.0`; source
  inspection shows changing only `_version.__version__` would not change the runtime
  default. No secrets or private material were printed.
- **Scoped fix direction:** Derive the default `ConnectConfig.app_version` from the
  canonical package version, or otherwise make the release process inject one shared
  value. Preserve the explicit override for hosts that intentionally advertise a
  different application version.

#### External-semantics review: no additional confirmed findings

- **Lifecycle/threading:** Python `socketserver` documents that `shutdown()` must be
  called while `serve_forever()` runs in another thread; `RemoteSocketServer` starts
  that loop in a daemon thread before calling `shutdown()`, and sets
  `block_on_close = False` for threaded request shutdown. The focused runtime tests
  passed, so I found no externally contradicted shutdown claim.
- **Zeroconf callbacks/discovery:** The official python-zeroconf API documents the
  `ServiceBrowser(zc, type_, handlers)` callback shape, `add_service`/`update_service`/
  `remove_service` lifecycle, `ServiceInfo` TXT/address fields, and `cancel()`/`close()`
  shutdown operations. The implementation uses those documented interfaces and
  tolerates `get_service_info()` returning `None`; no callback contract violation was
  established. The configured `ServiceInfo` default `other_ttl` is 4500 seconds and
  the reaper default is 4800 seconds, so the local safety expiry is not earlier than
  the documented default record TTL.
- **TLS fingerprint meaning:** Python documents `PEM_cert_to_DER_cert()` as returning
  DER bytes. The implementation hashes those DER certificate bytes with SHA-256 and
  compares the resulting fingerprint with `hmac.compare_digest()` after the TLS
  handshake. `client_context()` deliberately disables CA/hostname verification, but
  `TLSRemoteTransport` requires and checks the pinned certificate fingerprint; I found
  no evidence that the transport and identity fingerprints are currently conflated.
- **Packaging/installers:** Setuptools documents `tool.setuptools.dynamic.version` with
  an `attr` directive for a statically readable version attribute. The isolated build
  produced the expected wheel and metadata, and `scripts/verify_wheel.py` passed.
  Both installer checksum flows were inspected; no additional packaging failure was
  proven in this Linux-only environment. Windows installer execution and real LAN
  Zeroconf behavior were not available for this review.

### Finding-by-finding audit

1. **A1 identity fingerprint mismatch: supported, P1, high confidence.**
   `identity.py` hashes the bare node ID and returns 64 ungrouped hex
   characters. The mature reference hashes the explicit
   `system-analyzer-node:` namespace and returns colon-separated groups. The
   independent formula probe produced lengths 64 and 79 with equality false.
   The design says the façade preserves the mature core, and no protocol or
   namespace boundary was found. The reviewers correctly note that local
   self-comparison tests cannot detect this cross-package break. Physical
   two-node validation would strengthen interoperability evidence but is not
   required to establish the deterministic contract mismatch.

2. **A2 post-shutdown callback race: supported, P1, high confidence.**
   The generation/started check at `runtime.py:354-360` is separated from the
   validation, peer mutation, and callback delivery. My barrier probe blocked
   `_trusted_candidate_is_valid`, called `shutdown()`, then released it; the
   result was `stopped`, one peer retained, and one callback delivered. This
   directly violates the documented old-callback fencing and shutdown state
   boundary. The passing old-generation test is not contradictory: it tests a
   callback that begins after generation invalidation, not one already between
   the check and mutation.

3. **A3 discovery backend-construction failure: supported, P1, high
   confidence.** `NetworkDiscovery(...)` invokes the injected factory in its
   constructor before its own failure-safe `start()` path. The independent
   probe raised `RuntimeError`, left `status=starting`, and left `_server`
   present. `shutdown()` can clean this up only if the caller catches the
   unexpected exception and knows to call it; startup itself does not unwind or
   return a terminal status. This is a real partial-start lifecycle failure,
   not disproven by the normal unavailable-backend test.

4. **A4 invalid approval mutation: supported as P2, not P1 in its invalid
   input form.** `PairingManager.approve()` inserts before `_wire_grants()`
   converts permission strings. My probe got `ValueError` while the invalid
   grant remained in the owner. The resulting trust/live-state divergence is
   real. Agent 2's broader P1 concern is separately valid when the public
   approval API accepts valid destructive permissions: `PairingRequest` enforces
   read-only pairing, while `approve_pairing()` does not. The artifact should
   not collapse these two impacts: malformed-input partial mutation is P2;
   bypassing the mature read-only pairing boundary is a distinct P1 security
   contract issue.

5. **A3-1 network pairing handlers absent: supported, P1, high confidence.**
   `ConnectRuntime` constructs `RemoteSocketServer` without any pairing,
   confirmation, abort, or elevation handlers. The server's exact fallback is
   `pairing_unavailable`, and the runtime exposes no configuration seam for a
   host to supply them. The existing server test proves handlers work only when
   explicitly supplied, not that the public composition root supplies them.
   A host manually composing the low-level server is not a valid rebuttal to a
   productized `ConnectRuntime` whose stated responsibility includes pairing.

6. **A3-2 empty runtime capabilities: supported, P1, high confidence.**
   `_start_components()` hardcodes `frozenset()` while the listener advertises
   `connectable=True`. `RemoteService._solve()` checks required capability
   before grant permission, so even a valid read grant cannot complete `hello`
   or read operations. The independent composition probe confirmed the empty
   capability set. There is no `ConnectConfig` capability input, and the
   provider seam does not make an inert authorization surface a usable default.
   This is not contradicted by lower-level tests, which explicitly construct
   `RemoteService` with `READ_CAPABILITIES`.

7. **A3-3 persistence failure reported only as success: supported, P2,
   medium-high confidence.** The independent probe patched `JsonStateStore.save`
   to raise `OSError`; approval still returned a grant, runtime stayed started,
   and both pairing and live service state contained it. This may be an
   intentional best-effort policy, but it conflicts with the durable trust
   wording and the dedicated startup `PERSISTENCE_FAILED` state. The evidence
   proves a durability/result-reporting mismatch, not data loss during a
   successful atomic write. P2 is appropriate; P1 would overstate the direct
   impact absent a stronger persistence policy.

8. **A4 version drift: not confirmed as a current defect; retain as P2
   hardening evidence or needs-more-evidence.** The source has two version
   authorities: packaging/CLI use `_version.__version__`, while the runtime
   default is a literal. The current wheel and both values are `0.1.0`, so the
   reviewer did not reproduce an existing mismatch. The finding is a credible
   release-drift hazard and should not be called a confirmed runtime bug until
   a version-change or release-build counter-test demonstrates divergence.
